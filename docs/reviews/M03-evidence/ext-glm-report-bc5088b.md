## Findings

**[EXT-1] minor — formal/tr.pv:702–710@bc5088b — no reachability sanity for the honest run; every "true" query can be silently vacuous after a future model edit.** The gate (`xtask/src/gates.rs:1098` `proverif_check`) checks the 39 RESULT lines against `expect::PROVERIF_EXPECTED`. The three false queries (T7, T10, T12) prove attacker paths, but no query asserts that any `Recv`/`RecvKem` event is *reachable*: `inj-event(Recv(...)) ==> inj-event(Send(...))` (T2) and `event(RecvKem) ==> event(ChainKem)` (T11) are trivially true if a receive slot is unfillable. Evidence (model header, line 36): "the attacker can always deliver the accepted cell directly". I hand-verified that every slot in `sClean` *is* fillable (the DH/KEM terms of each honest cell match the receiver's derivations, incl. the `hopen(HKA)`-first branch at B's step 3), so the current verdicts are meaningful — but a typo in a future edit (e.g. a wrong `nhk_*` at a slot) would keep T1–T11 green while exercising nothing at that slot. Smallest fix: one informative query expected false, e.g. `query x: bitstring; event(Recv(sClean, pB, st3, c1, x)) ==> false.` (plus a CLAIMS line), so the gate fails if the honest run stops completing.

**[EXT-2] note — ref/secmp_ref/tr_cases.py:282–314@bc5088b — four §7.4 rejection paths have no frozen negative vector.** N1–N13 cover the five the milestone names plus eight more, but not: (a) step-path `pn < n_r` (replay via `pn`), (b) `pn`-gap over `MAX_FF` on a step's old chain (N10 covers only `n` on the chain path), (c) `n = u32::MAX` (`n_r += 1` overflow, §7.1 u32), (d) header opens under a skipped `hk` whose `(hk, n)` is absent → `break`-fall-through to `hk_r`/`nhk_r`. All four are covered in Rust (`reject_step_with_pn_below_n_r` tests.rs:636, `reject_gap_over_max_ff` tests.rs:748 ("step pn"), `reject_n_r_overflow` tests.rs:785, `reject_replay_of_a_consumed_skipped_key` tests.rs:723) and reachable by the fuzzer (mode 2–4 sealed headers), so these are not untested claims — but the frozen suite that also binds `ref/` is narrower than the tested matrix. Smallest fix: add the four rows at the next permitted vector freeze (spec revision), not now.

**[EXT-3] note — crates/secmp-proto/src/tr/ratchet.rs:484–493@bc5088b — one theoretically non-transactional refusal path, unreachable.** In `decrypt_with`, `self.apply(update)` runs before `self.to_bytes()`; if serialization failed there, `Refused::new(self, …)` returns the *mutated* state — the only path where a refusal is not byte-identical. Unreachable: `to_bytes` fails only on `skipped.len() > MAX_SKIPPED`/u16 overflow (state.rs:194, 223), and `apply` provably evicts to ≤ 512 (`select::evicted`, Kani `tr_eviction` kani_proofs.rs:348, test `state_skipped_count_bound`); the code comments say exactly this ("cannot fail: `apply` evicts `skipped` to its bound"). Kept as a note for the record; no fix required.

**[EXT-4] note — docs/03-protocol-spec.md:169 vs :468 — §4.2's SKIP_WINDOW gloss does not match §7.4's algorithm (code follows §7.4).** §4.2: "Skipped message keys retained **per receiving chain** … total bound 2 × SKIP_WINDOW". §7.4's own loop retains the last 256 positions *per `skip_message_keys` call*; across several gaps on the *same* chain the retained set accumulates (e.g. [744..1000) then [1000..1200) → 456 entries under one `hk`), bounded only by the 512 total. `select::skip_plan` (select.rs:109–118) implements §7.4 literally, as does `ref/tr.py:229–243`; both agree. Not a code deviation — a spec-wording observation the reviewer may want to record (no ADR/SQ entry covers it; SQ-22…27 do not).

**[EXT-5] note — ratchet.rs:548@bc5088b — already recorded internally, listed for completeness only.** `bool::from(any_skipped)` before decoding the selected skipped header is a second secret-dependent branch in decrypt (module doc, ratchet.rs:24–26: "two conversions … (M3 review C6) … branch-free variant is an M4 follow-up (review F1)"). Not re-reported as new.
