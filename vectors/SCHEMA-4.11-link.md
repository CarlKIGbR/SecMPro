Suite `link`, tag `link` (SCHEMA §3), file `vectors/link.json`, header `"schema": 6` and `"spec": "SecMP/1 rev 2.3"`
(SCHEMA §1). The suite has 86 cases, run by one client C and one relay R. There is one handshake, and then one link
("link A") on which every command case runs in event order. The case groups are:
- 27 positive cases: 5 for the handshake and 22 on link A;
- 23 command-error cases (E1–E23), in which the relay answers with an error;
- 1 indistinguishability case (X1);
- 8 RelayInfo cases: I1–I7 `relayinfo-reject`, plus I8, an accepting boundary case;

The order is as follows:
1. The positives and the command-error cases interleaved in event order, `link-0001` … `link-0050`. E1 and E2 sit

2. X1 (`link-0051`).
3. The RelayInfo cases (`link-0052` … `link-0059`).
4. `hs1-reject`, then `hs2-reject`, then `frame-reject` (`link-0060` … `link-0086`).

The cases of points 3 and 4 are each evaluated on a copy of a named state and change nothing.

Case *i* draws from its own stream (SCHEMA §2, suite name `link`, index *i*). Every stream-derived value is listed in
`inputs` in stream order: the client's draws first, then the relay's draws in response-frame order. The *derived*
values follow them. Ed25519 signatures (deterministic) and tokens (HMAC) draw nothing.

**Case shape (SCHEMA §1, `"schema": 6`).**
- **Common fields.** Every case has `id` (`link-0001` …), `op`, `party`, `from` and `inputs`.
- **`party`.** One of:
  - `"C"`: the client;
  - `"R"`: the relay;
  - `"CR"`: one request/response round trip on link A. C builds and seals, R opens, executes and answers, C opens.
- **`from`.** The id of the case whose state this case starts from:
  - in the handshake, the preceding step;
  - on link A, the preceding link-A case;
  - in a reject case, the base state named in its row.

  `link-0001` starts from no state and has no `from` **(proposal)**.
- **Link-A fields.** A link-A case also carries `cmd_seq`, a JSON number: the `cmd_seq` of its first request frame.
  `send-fill` also carries `count`.
- **Command-error case.** Carries `manipulation` and `outputs`, and no `expect`. The relay's answer is a defined
  response, not a rejection. Its `outputs` are `req`, `req_frames`, `resp`, `resp_frames`, `link_post` and
  `store_post` **(proposal)**: the manipulated token or signature is visible in `req`.
- **I8.** A `relayinfo-accept` case with `manipulation`. Its `outputs` are {`accept`}.
- **`expect: reject` case.** Carries `manipulation` and `"expect": "reject"`.
  - `relayinfo-reject`, `hs1-reject` and `hs2-reject` cases have no `outputs`, because no link exists yet. S10 is
    the exception and carries the outputs its row names.
  - A `frame-reject` case carries `outputs` = {`link_post`}, unchanged, as hx's `respond-reject` carries
    `opks_post`.
- **X1.** Carries `cases`, an array of arrays of case ids, instead of `from`.

**Values.** Values are lowercase-hex byte strings, except the following:
- `accept` is a JSON boolean.
- `req`, `req_frames`, `resp` and `resp_frames` are JSON arrays of byte strings in frame order.
  - `req`/`resp` hold the **unpadded** frame payloads `op ‖ cmd_seq ‖ fields` (docs/03:806). The padding to 4336 B is
    the §4.1 rule (docs/03:149) and is implied.
  - `req_frames`/`resp_frames` hold the 4352-B wire frames.
- `link_post` is a JSON object {`c2r`, `r2c`, `cmd_seq`} of numbers: the next frame counter in each direction
  (docs/03:566) and the relay's last recorded `cmd_seq` (reading OPEN-5).
- `store_post` is a JSON object {`queues`, `linkdata`}.
  - `queues` is an array, ascending by `rid`, of {`rid`, `sid`, `cell_ids` (numbers in queue order), `next_cell_id`}
    (docs/03:583).
  - `linkdata` is an array, ascending by `ld_id`, of {`ld_id`, `one_time`, `expires_bucket`, `present`, `consumed`}. A
    consumed one-time entry stays as `present` 0, `consumed` 1 (docs/03:610).
  - Hour buckets and `arrival` are not listed (docs/03:583, 624). They are relay-internal and never on the wire, and
    `arrival` matters only through the order of FETCH_MULTI responses.
- `resp_counts` (X1) is an array of arrays of numbers, and `frame_len` (X1) is a number **(proposal: its JSON shape)**.

**Keys from the stream** (SCHEMA §2).
- An X25519 secret is 32 raw bytes.
- An Ed25519 key is a 32-byte seed. This covers `relay_sig` and the queue keys `recv_pk`/`send_pk` and `owner_pk`,

  is ML-KEM-768 (docs/03:71).
- `m*` is `Encaps_internal` randomness.
- `relay_access_key`, cells, blobs, `ld_id` and dummies are raw stream bytes.

**What the byte-level test compares, per group.** docs/03:606 says "success and error frames are indistinguishable on
the wire" (see also the 07 M5 acceptance). The test checks four things:
1. The number of relay→client frames, which equals the D.2 count for the command (docs/03:597–602, 833).
2. The position of the response in the frame sequence: right after the command's last request frame. For LINK_PUT,
   that is after the third frame (docs/03:818).
3. The length of every frame: 4352 B (docs/03:163, 566).
4. The length of every plaintext before sealing: 4336 B, ISO/IEC 7816-4 padded (docs/03:149, 563).

Nothing else is observable on the wire. A frame carries no cleartext byte: there is no length prefix (docs/03:802),
and the nonce is implicit (docs/03:563). Equal counts, positions and lengths are therefore the whole wire-level claim.
That the contents cannot be told apart is the AEAD's property and cannot be tested from a vector. Timing is outside
the suite (M6).

`resp_counts` is the vector's statement of item 1. Items 2–4 hold for every case in the file, and the generator
asserts them.

#### Readings decided by the reviewer (planning-cell items OPEN-1 … OPEN-13)

- **Reading OPEN-1 — draw order** (docs/03:542, 549, 92–94).
  - C draws `e_c_sk`, `ek_c_seed`, `sk_e1`, then `m1`. R draws `sk_er`, then `m2`.
  - This is the HS1 field order combined with the §3.2 line order (X25519.keygen before ML-KEM.Encaps), as in
    REF-M3 reading 3.
  - Cases: P3, P4, S4, S10.
- **Reading OPEN-2 — LINK-level rejection** (docs/03:535, 548, 552, 566, 628).
  - A failed RelayInfo, HELLO, HS1, HS2 or frame check is one uniform error. The receiver emits nothing more (no
    RELAYINFO, HS2 or frame) and closes the connection.
  - Its counters, `cmd_seq` and store are unchanged.
  - R draws no HS2 randomness before `mac1` verifies.
  - Cases: I1–I7, H1, S1–S10, T1–T4, F1–F12.
- **Reading OPEN-3 — HS1 replay** (docs/03:556, 701; there is no HS1 cache).
  - R answers a replayed HS1 as a new handshake, with a fresh `e_r` and `ct_c`.
  - Replay resistance comes from `ss2`: the replayed first frame fails under the new `k_c2r`.
  - Case: S10.
- **Reading OPEN-4 — the 60-day bound** (docs/03:535).
  - The client MUST check `valid_until − now ≤ 60 days` and reject a RelayInfo that exceeds it. This makes the bound
    enforceable rather than an operator promise.
  - Exactly 60 days is accepted.
  - Cases: P2, I7, I8.
- **Reading OPEN-5 — `cmd_seq`** (docs/03:589).
  - `last` starts at 0.
  - Every request frame that opens and has `cmd_seq` > `last` records its `cmd_seq`, whatever the command's outcome.
  - `cmd_seq ≤ last` is answered with one ERR 6 (MALFORMED), and nothing is executed. CONT stays exempt.
  - Cases: E23; `link_post` everywhere.
- **Reading OPEN-6 — undecodable frames** (docs/03:149, 155, 628, 833; contrast docs/03:810).
  - A frame that opens but does not decode is a LINK-level rejection under reading OPEN-2: teardown, nothing
    emitted, counters unchanged. Bad padding and an unknown opcode are examples.
  - A CONT with no multi-frame command pending is rejected the same way.
  - SKEY (0x02) is the one reserved opcode that is answered, with ERR 6 (docs/03:810).
  - Cases: F10–F12, E21.
- **Reading OPEN-7 — the FETCH response layout** (docs/03:585, 597, 604, 827, 833; ref-log note L-3).
  - A FETCH error is answered with exactly `F` CELLR frames. Frame 1 has `present` ∈ {2, 3, 4}, `rid` set,
    `cell_id` 0 and a random cell. Frames 2 … `F` are dummies.
  - §9.1's "answer … with `ERR_MALFORMED`" reads as `present` = 4.
  - In a successful FETCH, the real cells come first, ascending by `cell_id`, and the dummies follow.
  - Cases: P12–P14, P21, E11–E14.
- **Reading OPEN-8 — FETCH_MULTI** (docs/03:598, 604, 827).
  - Each entry has the FETCH `ack` semantics: cells with `cell_id` ≤ `ack` are deleted first, and `ack ≥
    next_cell_id` gives `present` 4 for that entry.
  - The error frames come first, in request order.
  - A present-1 CELLR carries its queue's `rid`. docs/03:827 zeroes `rid` "for FETCH" only.
  - Cases: P18, E15.
- **Reading OPEN-9 — signature failures that §9.3 does not list** (docs/03:595, 599, 600; compare 596 and 629).
  - QUEUE_NEW, QUEUE_DEL and LINK_PUT answer a signature that does not verify with ERR 4 (AUTH). For LINK_PUT, the
    answer comes after the third frame (docs/03:818). The state is unchanged.
  - QUEUE_DEL of an unknown `rid` is answered with ERR 3. No case tests it.
  - Cases: E7, E16, E18.
- **Reading OPEN-10 — LINK_GET owner status with a signature that does not verify** (docs/03:601, 606, 610, 833).
  - The answer is three frames: LINKR {`present` 0, `consumed` 0, dummy blob}, then CONT, CONT.
  - This gives no existence oracle, and the frame count equals that of a success.
  - Case: E22.
- **Reading OPEN-11 — LINKR fields** (docs/03:601, 610, 827; ref-log note L-5).
  - The consuming call answers `present` 1, `consumed` 0.
  - The dummy blob is 12360 random bytes from R's stream, split 4160 / 4100 / 4100 like a blob.
  - Cases: P25–P27, E19, E20, E22.
- **Reading OPEN-12 — the budget** (docs/03:625).
  - `budget_queues` = 2 is a vector-only relay parameter. Queues count; link data does not.
  - "Exceeded" means a QUEUE_NEW that would create a third queue.
  - The table never sends an identical QUEUE_NEW at the limit.
  - Cases: E1, P15, P16.
- **Reading OPEN-13 — the first three frames each way** (docs/03:560, 784).
  - The frames are QUEUE_NEW, SEND and PING, at counters 0, 1 and 2.
  - A real client runs QUEUE_NEW on a one-shot link (docs/03:686). That is client behaviour, outside the suite.
  - Cases: P6–P8.

#### Readings from the spec text (quotable)

- **R-a. RelayInfo.**
  - The client verifies `sig`, `relay_fp`, `valid_until ≥ now` and `akc` (if it holds an access key), and never
    caches the info (docs/03:535).
  - `akc` = SHA-256(`"SecMP-Q/1 akc"` ‖ key) (docs/03:222).
  - I4 fails whether the client compares against the RelayRef's `akc` or against the commitment of its own key
    (docs/03:229), so no case depends on which.
- **R-b. Frames.**
  - `k_c2r` is used client→relay and `k_r2c` relay→client.
  - The nonce is 0^16 ‖ u64be(counter), and the AD is `"SecMP-LINK/1 frame"` ‖ `sess_id`.
  - The plaintext is padded to 4336 B.
  - Counters start at 0 in each direction and are strict +1 (docs/03:563–566).
  - `cmd_seq` is only strictly increasing (docs/03:589); P22 tests this.
- **R-c. Tokens.**
  - The token is bound to `sess_id` and to the command's own `cmd_seq` (docs/03:618).
  - A token from another `cmd_seq` or another link is therefore ERR_TOKEN (docs/03:595, 600).
  - v1 keeps no double-spend list (M13).
- **R-d. Identical QUEUE_NEW.**
  - An identical QUEUE_NEW (same `recv_pk` and `send_pk`) answers OK_QUEUE_NEW without side effects, although its
    token and signature differ.
  - A known `recv_pk` with another `send_pk` is ERR_AUTH (docs/03:595, 629).
- **R-e. Multi-frame commands.**
  - LINK_PUT is 3 frames of 4160 + 4100 + 4100 B, with ONE response after the third frame, failures included
    (docs/03:815, 818).
  - LINKR is followed by two 0xFF CONT frames (docs/03:828).
  - CONT repeats the `cmd_seq` and is exempt from the increase check (docs/03:589).
- **R-f. Eviction.**
  - Eviction removes the oldest cell and reports its `cell_id` with `evicted_present` 1.
  - `evicted_id` is 0 when `evicted_present` is 0 (docs/03:614, 826).
- **R-g. MALFORMED answers.**
  - SKEY is answered with ERR_MALFORMED (docs/03:810).
  - FETCH with `ack ≥ next_cell_id` is MALFORMED (docs/03:585), carried as `present` 4 (reading OPEN-7).
- **R-h. One-time link data.**
  - A one-time blob is deleted atomically by the first consume.
  - Later consume calls answer `present` 0, `consumed` 1.
  - Owner status never consumes (docs/03:610).
- **R-i. Strict Ed25519.**
  - The strict verification of docs/03:140 applies to RelayInfoV1.`sig` and to every D.2 `sig`. The byte rules apply
    at decode (docs/03:152).
  - No case depends on the strict extras: bad signatures are made with a wrong key, or (I1) by flipping the low bit
    of S.

#### Questions and readings of `ref/` (proposal)

None of these changes a byte of the file; each is a behaviour that §8/§9 and the readings above leave open, pinned so
that `ref/` is total. They are in `ref/SPEC-QUESTIONS.md` with the quotes.

- **SQ-26 — a request whose `cmd_seq` ≤ `last`, for a multi-frame command or a response of more than one frame**
  (reading OPEN-5 against docs/03:597–601, 818, 833). Reading used: one ERR 6 frame, also for FETCH, FETCH_MULTI and
  LINK_GET, whose D.2 count does not apply to a request that is not executed; for LINK_PUT the relay still takes the
  two CONT frames and answers that one ERR 6 after the third, as every LINK_PUT answer (reading R-e). Only E23 (PING,
  one frame either way) is in the suite.
- **SQ-27 — frames while a LINK_PUT is pending** (docs/03:589, 818; reading OPEN-6). Reading used: only the next CONT
  of the pending LINK_PUT (same `cmd_seq`, `idx` 1 then 2) continues it; any other frame — a CONT with another
  `cmd_seq` or `idx`, another command, SKEY — is a LINK-level rejection like the orphan CONT (ref check
  `cont-expected`). No case.
- **SQ-28 — FETCH_MULTI with more entries in error than `F_M`, or a repeated `rid`** (docs/03:598, 813: `count ≤ 32`,
  `F_M` = 8). Reading used: the first `F_M` error frames in request order and nothing else; a repeated `rid` is
  checked and acknowledged per entry, and its queue's cells are selected once. No case.
- Readings adopted without a question (`ref/SPEC-QUESTIONS.md`, "Readings adopted without a question — REF-M5"):
  the order of checks inside each command (QUEUE_NEW: token, signature, known `recv_pk`, budget; SEND: `sid`,
  signature; FETCH and each FETCH_MULTI entry: `rid`, signature, `ack`; QUEUE_DEL: `rid`, signature; LINK_PUT: token,
  signature, `ld_id` known; owner status: entry and signature together); SKEY parses nothing after `cmd_seq`; a
  LINK_PUT on a consumption marker is ERR 5 until the marker expires; a consume-mode LINK_GET of an entry that is not
  one-time returns it and keeps it; owner status draws its dummy blob whether or not the signature verifies, consume
  mode only when it returns no blob; the padding is checked when the frame is opened, before the request decoder;
  the RelayInfo checks run in the order listed under "ref check"; the JSON names and shapes marked above.
