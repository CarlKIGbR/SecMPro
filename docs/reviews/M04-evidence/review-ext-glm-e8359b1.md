## Findings

**[EXT-1] minor — `crates/secmp-proto/src/prekeys.rs:495` (and `:550`) @e8359b1 — `add_record` lets two records name one OPK; `retire_expired` deletes an OPK still referenced by an unexpired record.** Repro: `MemoryPrekeyStore::add_record` validates only *spk held, opk held, ld_id unique* — `store.rs:336` (`add_record_rejects_duplicate_ld_id_alone`) even demonstrates adding a second record while one exists. `add_record(Record{ld: A, opk: 1}); add_record(Record{ld: B, opk: 1})` → both `Ok`. Then either (a) A is accepted → `commit_accept(1, A)` consumes A and deletes OPK 1; B's invitee's honest handshake is rejected forever with the uniform `Rejected` (indistinguishable from garbage, §6.1 "one per one-time invitation" silently broken), or (b) A expires → `retire_expired` (`opks.retain(|o| !dead_opks.contains(&o.id))`) deletes OPK 1 while unexpired B still names it. Fails closed in both cases (no key reuse, no impersonation — the OPK is simply gone), and the sanctioned `issue_invitation` path always draws a fresh OPK; but the store's own documented invariant ("An OPK is used for exactly one invitation") is not enforced at the public boundary and has no test (`prekey_store_one_opk_per_invitation` covers only the issue path). Smallest fix: reject in `add_record` when any held record already names `record.opk_id`, plus one test row.

**[EXT-2] minor — `fuzz/corpus/` (repository state) @e8359b1 — no tracked corpus for the `hx_outer` fuzz target.** Evidence: `ls fuzz/corpus` → 20 directories; the 21 targets of `expect::FUZZ_TARGETS` include `hx_outer` (`fuzz/fuzz_targets/hx_outer.rs` exists, has a `FUZZ_MAX_LEN` entry and a `fuzzseed.rs` vector-seeding rule), but `fuzz/corpus/hx_outer/` does not exist — commit `3d62720` added tracked corpora for the other six M4 targets only. docs/06 §4 requires "corpora committed"; the smoke still exercises the target from the vector seeds each run, so no parser coverage is lost today, but no accumulated fuzzer knowledge exists for the Outer decoder and the gate passes a nonexistent directory to libFuzzer. Smallest fix: `mkdir fuzz/corpus/hx_outer` + commit the interesting inputs of one run (and optionally thin out or note the 2-file `inv_linkdata` corpus).

**[EXT-3] note — `crates/secmp-proto/src/hx/initiator.rs:244` + `hx/mod.rs:87` @e8359b1 — `start` returns the post-`first_msg` `RatchetState` by value while `HandshakeCells::release` persists the serialisation captured at `start` time.** A caller that first advances and persists the returned state and only then calls `release` makes the release transaction re-persist the older (`n_s = 1`) serialisation over the newer one — on restart the ratchet would re-derive the same message key (key-reuse footgun). The intended sequence (release before any further encrypt) is implied by the persist-before-send docs but not stated in `release`'s contract, and the type system permits the wrong order (the deliverable's `(HandshakeCells, RatchetState)` signature makes this unavoidable; a doc sentence or returning the state only through `release` would close it). No defect on the reviewed code paths; M7 sequencing must honour it.

**[EXT-4] note — `ref/secmp_ref/hx.py:330-401` @e8359b1 — the reference responder predates ADR-044 (c)/(e)/(f).** `respond` has no reflection check, no `n = 0`/`pn = 0` check, no known-route check, processes one complete group per call (REF-M4 reading 5, documented) and holds groups in an unbounded dict (no 8-slot bound, no continue-after-rejected-group). ADR-044's consequence "vectors unchanged (`hx.json` frozen at a33cf162…)" makes this accepted: none of the 30 frozen cases exercises those paths, so the cross-check is unaffected — but the ref is not at the code's spec revision for responder policy; anyone regenerating vectors after a future code change must not treat ref `Ok` as Rust `Ok` on those paths (the Rust tests N-33/N-57/N-66–N-70 carry them).

**[EXT-5] note — `crates/secmp-proto/src/prekeys.rs:289`, `wire/inv.rs:219-225` @e8359b1 — `link_key`/`inv_send_seed` (and `InvitationRecord.link_key`) are `SecretBytes`: zeroised heap, not `LockedSecret` (mlocked).** They live for the invitation's ≤ 30-day lifetime, longer than `SecretBytes`' documented "short-lived secrets" class (`secret.rs:13`); consistent with the crate's convention (all HX-derived keys are `SecretBytes`) and all copies are wiped on drop — noting the lifetime-class mismatch only.

**[EXT-6] note — `formal/hx/hClean-auth.pv:16` (and the four other `-auth` files) @e8359b1 — the O-24 search hints (`select`, `nounif … [ignoreAFewTimes]`) can in principle lose derivations**, i.e. a *true* verdict in the auth files is relative to the hinted resolution search (the direction that can hide an attack, not the one that fabricates one). Reviewer-accepted (O-24) with measured effects and `[ignoreAFewTimes]` mitigation; the expected-false rows (H8 in `hDH-auth`, H9 in `hKCI-auth`) still come out false under the hints, which is evidence the hints do not mask the modelled attacks. Recorded because the CLAIMS wording "never produce a wrong verdict" is stronger than what `nounif` guarantees for true verdicts.

**[EXT-7] note — `.github/workflows/ci.yml:3-4` @e8359b1 — `proverif-hx` and `mutants` are not owner-required checks** (header comment; ADR-046/047 make them reviewer-required for GO only). A merged PR is therefore not branch-protection-guaranteed to have run the HX formal gate or the mutation gate; process control covers it. `--strict` (skipped step ⇒ failure), the `--models tr|hx` split across two jobs that both run on PRs, and the expected-set equality checks close the other bypass routes I looked for (dispatch workflow has distinct job names; no `continue-on-error`; no `needs:` on required jobs).

**[EXT-8] note — `crates/secmp-proto/src/kani_proofs.rs:421-424` @e8359b1 — K3 proves grouping at `Groups<_,_,3>` / 4 ids / ≤ 6 inserts, not the production `MAX_PARTIAL_GROUPS = 8`** (documented STOP with the `GROUPING_SLOTS < MAX_PARTIAL_GROUPS` assert flagging it; the production bound is covered by test `group_partial_store_bound_8_evicts_oldest` and the generic code is identical). K4b proves `commit_accept` on two concrete one-record stores (the ≤ 2-record bound STOPs, report §11.3). Not vacuous: eviction is reachable (4 ids > 3 slots) and the K4 cover property (rejected group, then another init_id commits) is asserted via `kani::cover!`.
