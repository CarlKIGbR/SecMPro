### 4.9 `tr` — SecMP-TR transcript (spec §7)

*SCHEMA §4.9 as proposed by `ref/` for brief REF-M3 (2026-09-30), from spec rev 2.3 §7, §3.2–3.4 and App. A–D. The
reviewer's decisions in the brief are written down as given; what `ref/` adds is marked **(proposal)**, and the
readings it pinned for SQ-22 … SQ-24 are marked with the question. The tables are generated by
`ref/tools/render_schema_4_9.py` from `ref/secmp_ref/tr_cases.py`, the table that generates `vectors/tr.json`.*

Suite `tr`, tag `tr` (SCHEMA §3), file `vectors/tr.json`, header `"schema": 4` and `"spec": "SecMP/1 rev 2.3"`
(SCHEMA §1). 96 cases, one per event, in event order:
1 `init`, 40 `send`, 40 `recv`, 2 `advance`, 13 `recv-reject`.
Case *i* draws from its own stream (SCHEMA §2, suite name `tr`, index *i*). The ratchet takes its randomness from
that stream, every stream-derived value is listed in `inputs` in stream order, and the *derived* values follow them.

**Case shape (SCHEMA §1, `"schema": 4`).** Every case has `id` (`tr-0001` …), `op`, `party`, `inputs` and
`outputs`. `party` is the party whose state the event changes: `"A"` (the initiator) or `"B"` (the responder), and
`"AB"` for `init` **(proposal)**. The other case-level fields are ASCII strings, except `count`, which is a JSON
number. A `recv-reject` case carries `"expect": "reject"` **and** `outputs`, which hold its two state digests (they
are equal). Every value in `inputs` and `outputs` is a lowercase-hex byte string.

| op | case-level fields | `inputs`: stream order, then *derived* | `outputs` |
|---|---|---|---|
| `init` | `party` = `"AB"` | `sk` 32, `sb` 32, `spk_dh_sk` 32, `rpk_kem_seed` 64, `dh_s_sk` 32, `kem_s_seed` 64, `m` 32 | `state_post_A`, `state_post_B` |
| `send` | `party`, `msg` (`"m01"` … `"m40"`) | the Content's stream fields (below), `hdr_nonce` 24; *derived* `content` | `cell` (4096 B), `state_pre`, `state_post` |
| `recv` | `party`, `msg`, `from` (the id of the message's `send` case; the cell is not repeated) | on a DH step: `dh_sk` 32, `kem_seed` 64, `m` 32 (DHRatchet order); otherwise none | `content`, `state_pre`, `state_post` |
| `advance` | `party`, `count` | `hdr_nonces` = 24 × `count` bytes, one `hdr_nonce` per cell, front to back | `state_pre`, `state_post` |
| `recv-reject` | `party`, `msg` and `from` (the base message and its `send` case) **(proposal)**, `manipulation`, `expect` = `"reject"` | the manipulation's stream fields (only N2: `ek_pq_seed` 64); for N1 only, `dh_sk` 32, `kem_seed` 64, `m` 32; then *derived* `cell` | `state_pre`, `state_post` |

**Obligations per op.** An implementation reproduces every case from its inputs and the preceding cases:

- `init`: `SK` = `sk` and `sb` = `sb`. The responder's `SPK_dh` key pair is the X25519 secret `spk_dh_sk`; its
  `RPK_kem` key pair is `KeyGen_internal(d ‖ z = rpk_kem_seed)` (ML-KEM-768). A is the §7.2 initiator with `dh_r` =
  X25519(`spk_dh_sk`, 9) and `kem_r` = the RPK `ek`; it draws `dh_s_sk`, `kem_s_seed` and `m` (dh_s keygen, kem_s
  keygen, `Encaps_internal(kem_r, m)`). B is the §7.2 responder and draws nothing. Both digests must match.
- `send`: Encrypt(state, `content`) (§7.3), with `hdr_nonce` as its randomness. `content` is the unpadded encoded
  Content (§7.6, D.5), and Encrypt pads it to `BODY_LEN` = 1710 (ISO/IEC 7816-4). The cell must equal `cell`, and
  the digests must match.
- `recv`: Decrypt(state, the `cell` of the case `from`) (§7.4), with `dh_sk`, `kem_seed` and `m` as DHRatchet's
  randomness (dh_s keygen, kem_s keygen, `Encaps_internal(kem_r, m)`). `inputs` is non-empty exactly when the
  message triggers a DH step. The plaintext, unpadded, must equal `content`, which is the sender's `content`.
- `advance`: `count` × Encrypt(state, Dummy), each with the next 24 bytes of `hdr_nonces`. The cells are discarded
  (lost in transit), and only the state digests are compared. The Dummy Content is `ver` 1, `type` 0x00, `seq` 0,
  `ts` 0, empty body **(proposal)**. No byte of the file depends on it.
- `recv-reject`: Decrypt(state, `cell`) fails with the implementation's single uniform error, and the state is left
  exactly as it was: `state_post` = `state_pre` (§7.4 note (c), transactional decrypt). N1 is rejected by the body
  MAC after DHRatchet has run on the working copy, so it lists DHRatchet's randomness like a `recv`.

**State digest** (brief REF-M3). It is a comparison construct of this suite, not a persistence format:

```
StateDigestV1 = SHA-256( "SecMP-TR/1 state-digest" ‖ sb ‖ rk ‖ dh_s.sk[32] ‖ opt(dh_r) ‖ kem_s.seed[64 = d ‖ z]
                ‖ opt(kem_r) ‖ opt(last_ct_r) ‖ opt(ct_s) ‖ opt(ck_s) ‖ opt(ck_r) ‖ opt(hk_s) ‖ opt(hk_r)
                ‖ opt(nhk_s) ‖ opt(nhk_r) ‖ u32be(n_s) ‖ u32be(n_r) ‖ u32be(pn) ‖ u32be(|skipped|)
                ‖ Σ_{entries in insertion order} ( hk[32] ‖ u32be(n) ‖ mk[32] ) )
opt(None) = 0x00 ; opt(Some(x)) = 0x01 ‖ x ; dh_s.sk = the 32 raw bytes as drawn (before clamping);
the ASCII label has no terminator.
```

The preimage contains every field of §7.1, so equal digests mean equal states. The label is not an App. A label
(SQ-24).

**Content per message.** Every Content has `ver` 1, `seq` = the message number (m07 → 7), `ts` = 1 700 000 000 +
`seq`, and is padded per D.5.

**KeyChange** (m18–m21). KeyChange = new IKSPublic ‖ HybridSign(old `IK_sig`, `"SecMP-TR/1 keychange"`,
fingerprint(new IKSPublic)) (§7.6, §3.5, §6.2). The old `IK_sig` is Ed25519 seed `old_ik_ed_seed` ‖ ML-DSA-65
`KeyGen_internal(old_ik_mldsa_xi)`, and the ML-DSA part is hedged with `rnd`. The new IKSPublic is `ver` 1,
`ik_ed25519` from `new_ik_ed_seed`, `ik_mldsa65` from `new_ik_mldsa_xi`, and `ik_dh` = X25519(`new_ik_dh_sk`, 9).
The reassembled bytes `0x05 ‖ KeyChange` (5391 B) are cut into maximal chunks of 1669 B (1689 − 20),
with the remainder last: 1669 B, 1669 B, 1669 B, 384 B.
All four fragments carry the same `msg_id`, `total` = 4 and `idx` = 0 … 3.

**m05 (SQ-22).** The brief's "m05 Batch L=1689" cannot be one cell: a Batch body is 24 + L bytes and `body_len` ≤ 1689
(§7.6), so L ≤ 1665. `ref/` pins **L = 1665**, which makes the body exactly 1689 B, the largest one-cell Batch.
This touches only the bytes of `content` and `cell` in the m05 `send` case and of `content` in its `recv` case.
No state digest depends on it.

#### Negative events

"ref check" names the check of the reference Decrypt that fires. It is informational; only the uniform rejection
and the unchanged state are compared. The checks are `cell-length` (split: the cell is not 4096 B), `no-header-key`
(no skipped hk, `hk_r` or `nhk_r` opens the header), `header-decode` (the header opens but HeaderV1 decoding
rejects), `step-same-dh` (a step with `dh_pk` = `dh_r`), `kem-constancy` (a non-step header whose `ek_pq`/`ct_pq`
differs from `kem_r`/`last_ct_r`), `replay` (`until` < `n_r`), `max-ff` (a gap > `MAX_FF`) and `body-mac`
(MsgDecrypt). Where a well-formed header is needed, the header is re-encoded and sealed again with the sender's
header key under the base cell's own `hdr_nonce` and AD `"SecMP-TR/1 hdr" ‖ sb`, and the body is unchanged
**(proposal: same nonce)**.

#### Transcript

The delivery order is the event order. Within a phase, the sender's `send` events come first, in send order, and
the deliveries follow in delivery order; phases 5 and 9 interleave as the brief writes them **(proposal)**. A
negative event sits immediately before or after the delivery the brief names. For a `send`, `pn`/`n` are the
header's; for a `recv`, they are the delivered header's; for an `advance`, `n` is the range of the discarded
cells. "|skipped|" is the party's `skipped` after the event, "Δ" the entries inserted (+) and removed (−), and
"path" says whether the message was decrypted through §7.4 step 1 (`skipped`) or on a chain.

- **Phase 0** — initialisation
- **Phase 1** — A→B m01 Batch L=100, m02 Dummy, m03 Batch L=500; delivered in order (B steps on m01)
- **Phase 2** — B→A m04 Batch L=100, m05 Batch L=1665 (SQ-22), m06 Dummy; in order (A steps on m04) — round trip 1
- **Phase 3** — A→B m07–m10 Batch L=64; delivered m09, m07, m10, m08 (B steps on m09)
- **Phase 4** — B→A m11–m13 Batch L=32; m11 is not delivered now; A receives m12 (a step on a non-first message of the chain, §7.4 note (d)), then m13 — round trip 2
- **Phase 5** — A→B m14 Batch L=16, delivered; advance A 10000; A→B m15 Batch L=16, delivered (B fast-forwards 10 000 positions and stores 256 keys)
- **Phase 6** — B→A m16, m17 Batch L=200; in order (A steps on m16)
- **Phase 7** — A→B m18–m21 = the four Fragments of one KeyChange; in order (B steps on m18)
