## 2. Findings

### L1-01 · minor · `crates/secmp-proto/src/tr/content.rs:257-264`@665e84e (with `:137-145`)
- **Obligation:** spec §7.7 "Unsigned/unverifiable changes freeze the session with a warning. No 'just accept'
  path."; CLAUDE.md §1.5 fail closed ("Verification failure → drop, freeze, warn").
- **Reasoning:** a reassembled payload with `inner_type` 0x05 whose body fails `KeyChangeBody` decoding is
  `Delivery::Malformed` with `trust` unchanged; only a decodable KeyChange with a wrong signature reaches
  `key_change()` and freezes. Since §4.1 (b) moves part of signature checking into the decoder (Ed25519 `S ≥ L`,
  small-order/non-canonical `R`) and the new IKS is decoded with key checks (low-order `ik_dh`, bad `ik_ed25519`),
  these unverifiable key changes are discarded silently: no freeze, no warning, real sending stays allowed.
- **Repro (probe, scratch crate against the pinned crates, KeyChange in 4 fragments through a real session):**
  valid → `["Partial"×3, "KeyChange"]`, `KeyChanged`; signature by another key → `"KeyChangeRefused"`, `Frozen`;
  same KeyChange with Ed25519 `S = 0xff…ff` → `"Malformed"`, trust stays `Verified`, `may_send_real = true`; new IKS
  with `ik_dh = 0^32` signed correctly by the old key → `"Malformed"`, `Verified`.
- **Impact:** inconsistent fail-closed semantics; a peer (or anyone holding its ratchet keys) can present an
  identity-succession attempt the user is never warned about. Bounded: the content is ratchet-authenticated and the
  identity is not replaced.
- **Smallest fix:** in `Inbox::fragment`, if the reassembled bytes start with 0x05 and do not decode, apply the
  `key_change` failure branch (`Trust::Frozen`, `KeyChangeRefused`); or the judge records the opposite reading in
  the SQ-26 answer. Add the two probe cases as tests.
- **Status:** CONFIRMED (behaviour, probe); the spec reading ("undecodable = unverifiable") is for the judge (SQ-26).
  Confidence high.

### L1-02 · note · spec §4.2 `SKIP_WINDOW` vs §7.4 `skip_message_keys`; `crates/secmp-proto/src/tr/select.rs:105-114`@665e84e
- **Obligation:** §4.2 "Skipped message keys retained **per receiving chain**: 256"; §7.4 comment "older positions can
  no longer arrive (relay capacity)".
- **Reasoning:** the normative pseudocode bounds storage per *call*, not per chain; code, ref and frozen vectors
  follow the pseudocode. Python replay: after tr-0070 B holds **257** keys of one chain (positions 44…301); after
  tr-0074, n_r = 307 and position 44 (263 behind) is still stored, only the 512 total bound evicts.
- **Impact:** none on interoperability (both implementations and the vectors agree); spec text is inconsistent with
  itself. A per-chain reading would change frozen vectors (tr-0070…0075).
- **Smallest fix:** next spec revision: reword §4.2 to "stored per `skip_message_keys` call (window 256 behind
  `until`); total bound 2 × SKIP_WINDOW". No code change.
- **Status:** CONFIRMED (replay). Confidence high.

### L1-03 · nit · `crates/secmp-proto/src/tr/state.rs:278-298, 328-349`@665e84e
- **Obligation:** the module's own contract "Decoding is total and canonical … the shape of a reachable state"
  (`state.rs:21-28`); spec §7.1 `skipped` is a map (unique keys).
- **Reasoning:** the shape check does not relate `skipped` to the receiving chain: an entry `(hk_r, n)` with
  `n ≥ n_r` is accepted, though no reachable state has one. The next decrypt with a gap re-inserts `(hk_r, n)` (a
  duplicate key), and the resulting state's own encoding is rejected by `from_bytes`.
- **Repro (probe `probe/src/bin/state.rs`):** B receives position 2 (stores 0, 1; n_r = 3); last entry's `n` set to
  8 → `from_bytes` **accepts**; deliver position 12 → `to_bytes` ok, `from_bytes` of it = `Err(Rejected)` (session
  cannot be reloaded).
- **Impact:** only via a corrupted or forged persisted record (the store is authenticated, M7); not reachable from
  the wire.
- **Smallest fix:** in `from_bytes`, reject entries whose `hk` equals `hk_r` (ct_eq) with `n ≥ n_r`, and require that
  group, if present, to be the last.
- **Status:** CONFIRMED (probe). Confidence high.

### L1-04 · nit · `crates/secmp-proto/src/tr/ratchet.rs:481-490`@665e84e
- **Obligation:** documented contract "The state is unchanged" for every `Refused` (`ratchet.rs:90-92, 461-463`).
- **Reasoning:** if `to_bytes` failed after `self.apply(update)`, `Refused::new(self, error)` would return the
  *advanced* state (message key consumed, plaintext dropped). `encrypt_with` restores the previous fields in the
  same situation (`ratchet.rs:397-412`); `decrypt_with` does not. The branch is unreachable today (`apply` evicts to
  ≤ 512, the only `to_bytes` error).
- **Impact:** none now; a future fallible field in `to_bytes` would silently break transactional decrypt.
- **Smallest fix:** serialise a state built from the update before swapping it in, or keep the pre-apply values.
- **Status:** CONFIRMED (code reading; unreachable). Confidence high.

### L1-09 · note · spec §7.4 step check (`ratchet.rs:627-631`@665e84e)
- **Reasoning:** `header.dh_pk == dh_r` is byte equality, as the spec writes it and as §3/§4.1 keep keys "as
  received"; a non-canonical encoding of the same point (top bit set, or u + p for small u) passes it. The non-step
  path checks KEM constancy but not `dh_pk` constancy (as written). Only the holder of `nhk_s`/`hk_s` (the peer) can
  produce either header, and our side still mixes a fresh `dh_s`; no key reuse results.
- **Impact:** none on the code; a spec precision question. **Status:** CONFIRMED (spec reading). Confidence medium.

### L1-10 · note · SQ-25 "chunks of any size are accepted" (`content.rs:15-21, 197-265`@665e84e)
- **Reasoning:** spec §7.6 forbids `total = 1` because it "would be a second encoding of an unfragmented Content",
  but accepting arbitrary chunkings admits many fragmentations of one message, including fragmenting content that
  fits one cell — the same multiplicity. The vectors use maximal chunks (1669 … remainder last).
- **Fix (for the judge's SQ-25 answer):** either pin "every chunk but the last is 1669 B, the last 1…1669 B,
  `total` = ⌈len/1669⌉ ≥ 2" (and reject other shapes), or accept the multiplicity explicitly as a reassembly rule.
- **Status:** CONFIRMED (code reading). Confidence high.

## Findings

### L2-01 · minor · `crates/secmp-proto/src/tr/content.rs:257-263@665e84e` (with `wire/cell.rs:513-519`, `keys.rs:156-161`)

- **Obligation.** docs/03 §7.7 "Unsigned/unverifiable changes freeze the session with a warning. No 'just accept' path."; CLAUDE.md §1.5 "Verification failure → drop, freeze, warn"; SQ-26 reading (`docs/reviews/ref-spec-questions-M3.md:44`).
- **Reasoning.** A reassembled payload `0x05 ‖ IKSPublic ‖ sig` is decoded by `FragmentPayload::decode`; `KeyChangeBody::decode_from` decodes `sig` as `HybridSig`, whose `from_bytes` runs the §4.1 (b) Ed25519 encoding checks (`keys.rs:156-161`). Any decode failure lands in `Err(_) => Delivery::Malformed` (`content.rs:263`) **before** `key_change()` (`content.rs:137-145`) is reached, so `trust` is untouched and the session keeps delivering and sending. Consequence: an *unsigned* key change — the all-zero signature, whose Ed25519 `R` = (√−1, 0) has order 4 — and any change with `S ≥ L`, a small-order `R`, or a new IKS that fails decoding (e.g. low-order `ik_dh`) is silently dropped; only a well-encoded but wrong signature freezes. Which reaction occurs is chosen by the sender's byte choices.
- **Repro.** Probe `l2_unsigned_or_misencoded_key_change` (appendix A): four payloads, each fragmented (4 × ≤1669 B) and followed by a Batch, received with `Trust::Verified`:
  `all-zero signature (unsigned)`, `Ed25519 S >= L`, `Ed25519 R small order`, `new IKS ik_dh low order` → every one: `["Partial","Partial","Partial","Malformed","Messages"] trust=Verified may_send_real=true`. Contrast `content_unverifiable_key_change_freezes` (`tr/tests.rs:2299-2346`), which covers only well-encoded wrong signatures (→ `KeyChangeRefused`, `Frozen`).
- **Impact.** No acceptance path exists (the key is never accepted — authentication holds). What is lost is the tripwire: a party able to inject authentic E2E content (the peer, or an attacker holding a compromised session state before PCS heals) can attempt an unauthorised identity change without freezing the session or warning the user, contrary to the literal "Unsigned … changes freeze". Not exploitable for impersonation; hence minor, not major.
- **Smallest fix.** In `Inbox::fragment`, when the reassembled `whole` starts with `0x05` and `FragmentPayload::decode` fails, set `*trust = Trust::Frozen` and return `Delivery::KeyChangeRefused` (the §4.1 decoder obligations stay as they are; only the content layer's reaction changes). Add the four cases to `content_unverifiable_key_change_freezes`. Record the reading as an SQ-26 amendment (is an undecodable `KeyChange` an "unverifiable change"? — judge decides; an unfragmented type-0x05 Content can stay `Malformed`, it cannot carry a key change).
- **Status.** CONFIRMED (probe run + deterministic reading). Confidence high on behaviour; the severity depends on the judge's reading of "unsigned".

### L2-02 · note · `crates/secmp-proto/src/tr/ratchet.rs:655-660@665e84e`, `:443`, `error.rs:6-24`

- **Obligation.** J5 / M2 F4: `Error::Unavailable` never from attacker-controlled input, never distinguishable to peer/relay; CLAUDE.md §4 "authentication failures must produce indistinguishable errors"; §10.1 constant-rate invariant.
- **Reasoning (holds).** Every call on the decrypt path before the body MAC returns only `Rejected` or is infallible: `SecretBytes::from_slice` is heap-only and fails only on length (`secmp-crypto/src/secret.rs:100-107`); `Aead::open_ct` returns a `Choice` (`aead.rs:82`); `kdf_ck`/`kdf_rk` (`tr_kdf.rs:55-90`); `MsgEncrypt::open` (`msg.rs:106-121`); `decapsulate` is infallible (`mlkem.rs:93`); `diffie_hellman` rejects only an all-zero output (`x25519.rs:61-68`); `HeaderV1::decode` and the key decoders allocate no locked memory. `Unavailable` therefore arises only (a) in `open_step` after `MsgEncrypt::open` succeeded (`ratchet.rs:655` then draws at `:658-660`), i.e. only for an authentic DH-step cell from the peer; (b) at the nonce draw of `encrypt` (`:443`); (c) at `init_initiator_with` (`:307-309`); (d) in `RatchetState::from_bytes` after full validation (`state.rs:299-301`). The relay cannot forge a step cell; the peer cannot make the OS RNG or `mlock` fail (each step holds at most two extra locked pages transiently).
- **Residual (for M6/M7, not an M3 defect).** (i) The documented caller contract is "Unavailable → neither send nor acknowledge, retry" (`ratchet.rs:91-92`, report D1) while nothing specifies the ack for `Rejected`; if `Rejected` is acked and `Unavailable` is not, the relay sees a non-advancing ack exactly on an authentic step cell under local resource failure (leaks only the local failure). (ii) "retries the slot" on an `encrypt` `Unavailable` collides with §10.1 (a slot must emit its pre-built frame); M6 must define the fallback. (iii) Wording: `error.rs:9`, `:21` "never depends on input" / "never input-dependent" — it can arise only on an authentic step cell; "never attacker-producible" is the accurate claim.
- **Repro.** Probes `l2_every_byte_flip_rejects` (3 × 4096 single-byte flips of a step cell, a chain cell and a skipped-path cell) and `l2_random_cells_never_unavailable` (2000 random cells, before and after the responder's first step): all `Rejected`, `TestEntropy.calls == 0`, `to_bytes()` byte-identical, honest cells accepted afterwards. Existing `unavailable_step_consumes_nothing` (`tr/tests.rs:1042`) shows (a).
- **Status.** CONFIRMED (J5 holds at the TR layer); residual items are forward-looking.

### L2-03 · note · `crates/secmp-proto/src/tr/content.rs:74-87@665e84e`, `ratchet.rs:182-188`

- **Obligation.** docs/03 §7.7 "block outgoing messages until re-verification"; §7.5 persist-before-ack.
- **Reasoning.** Blocking is provided only as the predicate `Trust::may_send_real()`; `RatchetState::encrypt` takes no `Trust`, so any caller can encrypt real content in `KeyChanged`/`Frozen`. `Trust` and `Inbox` are caller-held values; `Opened::commit` hands its closure only the ratchet bytes. If the caller commits the ratchet state but persists `Trust::Frozen` separately and crashes between the two, the KeyChange cell is acknowledged and never redelivered — the freeze is lost permanently. Both are explicitly M7 work (docs/07 M7 E2E "key-change flow blocks sending until re-verified"; report §7 "storing them atomically … is M7's"), and the API makes the right composition possible (`Inbox::to_bytes` can be written inside the same `commit` closure).
- **Impact/fix.** None for M3. Carry to the M7 brief as two review-focus items: enforcement of `may_send_real` at the single send entry point, and one atomic commit of ratchet state + `Inbox` + `Trust`.
- **Status.** CONFIRMED (deterministic reading). Confidence high.

### L2-04 · note (threat-model residual) · `crates/secmp-proto/src/tr/ratchet.rs:690-717@665e84e`; docs/01 §3.5, §7

- **Obligation.** docs/01 §3.5 ADV-T "Cannot decrypt past traffic (FS)"; §3.7 "forward secrecy limits the blast radius to the future"; docs/03 §11.1 "forward secrecy per message".
- **Reasoning.** Skipped keys leave `skipped` only when used (`:691-693`) or evicted by later insertions (`:714-716`); there is no time-based expiry (docs/03 §7.4 defines none — the code conforms). Under normal operation few gaps occur, so a key for a cell that never arrived can stay for months. A relay (ADV-R) that silently withholds a few cells — it cannot tell real from dummy, but can sample — and later obtains the device store (ADV-T with the passphrase, or ADV-P) decrypts the withheld cells with the retained keys (≤ 512 of them, with their header keys). This is the classic Double Ratchet trade-off, but docs/01 states FS without the qualification and the RR register (docs/01 §7) has no entry for it.
- **Fix.** Spec/threat-model level only: add an RR entry ("skipped keys retained until consumed or evicted; cells withheld by the relay stay decryptable by a later device compromise"), or a spec revision adding an age bound (e.g. drop skipped entries of chains older than N steps). No code change at M3.
- **Status.** CONFIRMED (deterministic reading; no eviction or expiry path besides `apply`). Confidence high.

### L2-07 · nit · `crates/secmp-proto/src/tr/ratchet.rs:481-490@665e84e`

A party able to inject E2E content can freeze the session (spec-intended DoS) — or, per L2-01, can avoid freezing it.

## Fan-out (hypotheses for verifiers / other lenses)

- **FO-1 (L3).** The absent-key stand-in is the public all-zero key (`ratchet.rs:519`): a relay-crafted header sealed under it *opens* in the absent slot (masked to "not opened", correct — `reject_absent_and_unknown_keys`). `chacha20poly1305` decrypts only after tag success, so that slot then does 2330 B of extra keystream work: an input-controlled timing difference on the reject path of a responder before its first step / an initiator before its first reply. Not network-visible under §10.1 pre-built frames; L3 to judge against ADR-041.
- **FO-2 (L6).** L2-06: add the no-draw assertion to `fuzz/fuzz_targets/tr_decrypt.rs`.
- **FO-3 (judge).** L2-01 needs a reading: is an undecodable `0x05` reassembled payload an "unverifiable change"? Proposed: yes → freeze.
- **FO-4 (L4).** `kdf_ck` clones a keyed HMAC state (`secmp-crypto/src/tr_kdf.rs:77-90`); a keyed HMAC state is equivalent to `ck` for deriving the chain forward. `hmac = 0.13.0` with feature `zeroize` (`Cargo.toml:44`) — verify that `Hmac<Sha256>` (and the clones) zeroise on drop, else old chain keys survive in stack residue.
- **FO-5 (M6/M7 briefs).** Ack policy for `Rejected` vs `Unavailable`; slot fallback on an `encrypt` `Unavailable`; atomic commit of ratchet state + `Inbox` + `Trust`; enforcement of `may_send_real`; §7.8 reset flow; RR entry for L2-04. Also M4: until the responder's first step its `dh_s`/`kem_s` are the bundle's SPK/RPK secrets (§7.2), so they are serialised into `RatchetStateV1` if a responder state is ever persisted before its first successful decrypt — SPK/RPK deletion must cover such records.

/// L2-P1: a KeyChange whose signature is absent (all zero) or whose Ed25519 half is not a valid encoding
/// (S >= L, small-order R): what does the content layer deliver, and does the session freeze (spec §7.7)?
#[test]
fn l2_unsigned_or_misencoded_key_change() -> Result<()> {
    let (old_sk, old_iks) = identity(1)?;
    let peer = content::ik_sig(&old_iks)?;
    let (_, new_iks) = identity(2)?;
    let valid = key_change(&old_sk, Label::TrKeychange, &new_iks, &new_iks)?;
    let sig_at = sum(&[1, IKS_PUBLIC_LEN]);
    let mut unsigned = valid.to_vec();
    for b in unsigned.iter_mut().skip(sig_at) { *b = 0; }
    let mut s_big = valid.to_vec();
    for b in s_big.iter_mut().skip(sig_at + 32).take(32) { *b = 0xff; }
    let mut r_small = valid.to_vec();
    put(&mut r_small, sig_at, &U_ONE);
    let mut bad_iks = valid.to_vec();
    put(&mut bad_iks, sum(&[1, IKS_PUBLIC_LEN - 32]), &U_ONE); // ik_dh low order
    for (what, payload) in [
        ("all-zero signature (unsigned)", unsigned),
        ("Ed25519 S >= L", s_big),
        ("Ed25519 R small order", r_small),
        ("new IKS ik_dh low order", bad_iks),
    ] {
        let mut contents = fragments(1, &payload, 1669)?;
        contents.push(text(9));
        let pts = plaintexts(&contents)?;
        let order: Vec<usize> = (0..pts.len()).collect();
        let mut trust = Trust::Verified;
        let ds = receive_all(&mut Inbox::new(), &pts, &order, &peer, &mut trust)?;
        eprintln!("L2-P1 {what}: {:?} trust={:?} may_send_real={}", kinds(&ds), trust, trust.may_send_real());
    }
    Ok(())
}

/// L2-P2: every single-byte change of a step cell, a chain cell and a skipped-path cell is `Rejected`,
/// draws no randomness, leaves the state byte-identical; the honest cell is accepted afterwards.
#[test]
fn l2_every_byte_flip_rejects() -> Result<()> {
    let (a, b) = session()?;
    let (a, m0) = send(a, &text(0))?;
    let (a, m1) = send(a, &text(1))?;
    let (a, m2) = send(a, &text(2))?;
    let mut b = b;
    for i in 0..CELL_LEN { b = rejects(b, &flipped(&m0, i), "step cell flip")?; }
    let (b, _) = recv(b, &m0)?;
    let mut b = b;
    for i in 0..CELL_LEN { b = rejects(b, &flipped(&m2, i), "chain cell flip")?; }
    let (b, _) = recv(b, &m2)?;
    assert_eq!(b.skipped.len(), 1);
    let mut b = b;
    for i in 0..CELL_LEN { b = rejects(b, &flipped(&m1, i), "skipped cell flip")?; }
    let (b, got) = recv_seq(b, &m1)?;
    assert_eq!(got, 1);
    assert!(b.skipped.is_empty());
    let _ = a;
    Ok(())
}

## J9 — header-key selection: the answer

- **Which keys, which order, every call.** `open` opens the header under every distinct header key of `skipped`
  (first-seen = insertion order, `distinct_skipped_keys`, `crates/secmp-proto/src/tr/ratchet.rs:495-506@665e84e`),
  then `hk_r`, then `nhk_r` (`ratchet.rs:522-530@665e84e`); all of them, unconditionally, on every call (an
  `Iterator::map` + two calls, no early exit). An absent `hk_r` is replaced by an all-zero dummy key and its result
  masked with `present` (`ratchet.rs:261-272`, `:519@665e84e`). Order matches spec §7.4 (skipped → `hk_r` → `nhk_r`).
- **Does it stop at the first success?** No. The per-key verdicts are `Choice`s (`Aead::open_ct`,
  `crates/secmp-crypto/src/aead.rs:82-106@665e84e`); `select::first_opened` builds a one-hot of the first skipped key
  that opened with `&`, `|`, `!` (`select.rs:39-50@665e84e`); header bytes and key of that slot are selected with
  `conditional_assign` over every candidate (`ratchet.rs:533-543`); the `(hk, n)` lookup scans **every** entry with
  `ct_eq` on `hk` and `n` and records the index with `conditional_assign` (`ratchet.rs:551-558`); `select::decide`
  reduces the four `Choice`s to a code and branches once (`select.rs:62-81`).
- **How is the skipped map keyed and searched?** A `VecDeque<SkippedKey{hk, n, mk}>` in insertion order
  (`state.rs:89-93`, `:134@665e84e`); no hash map, no table indexed by secret data; linear constant-time scan. The only
  secret-position memory accesses are on the accept path: `self.skipped.get(at)` (`ratchet.rs:563`) and
  `VecDeque::remove(at)` (`ratchet.rs:692`, cost O(min(at, len−at)) moves) — L3-08.
- **Does it leak which key matched?** Error: no — every rejection is `Error::Rejected` (`Unavailable` only after the
  body MAC on a step). Timing: the *case* (skipped hit / chain / step / reject) is visible by design — the paths do
  different, spec-mandated work (evidence medians on M1 Pro: reject at header 9.58 µs, at KEM constancy 14.25 µs, at
  body MAC 17.58 µs; L3-05) — and the AEAD opens verify-then-decrypt, so "some key opened" costs one keystream pass
  more (`aead.rs:9-14@665e84e`; `chacha20poly1305-0.11.0/src/cipher.rs:85-97`, `if self.mac.verify(tag).is_ok() {
  apply_keystream }`). *Which* skipped key opened is not leaked by the selection (one-hot, constant work) but the
  consumed entry's position is (L3-08). One early `Choice`→`bool` conversion exists (L3-01); it adds no bit beyond
  the verify-then-decrypt pass.
- **Verdict on J9:** design-acceptable leaks only (case and accept-path position, both inherent in §7.4's sequential
  control flow); one guardrail letter violation (L3-01); the constant-time selection is not covered by any ct target
  (L3-02).

  `wire/cell.rs:134@665e84e`) → constancy rejects (`ratchet.rs:594-598`). The evidence medians are ordered by path

- **J4 conclusion:** the move does not change what the gate measures; the method is ADR-038 (1)(3)(4) + ADR-041 +

## Findings

### L3-01 · minor · `crates/secmp-proto/src/tr/ratchet.rs:545-549@665e84e`
- **Obligation:** docs/06 §9 ("constant-time results (`Choice`, `ct_eq`) turned into `bool` before being combined with
  another check … convert exactly once, at the final decision"); the implementer's own claim in plan D3
  (`docs/reviews/M03-report.md:81-89@665e84e`: "converted to a `bool` exactly once, at the final branch"),
  `select.rs:4-7@665e84e` ("one conversion at the end"), `ratchet.rs:21-24@665e84e`.
- **Reasoning:** `any_skipped` is converted with `bool::from` at `ratchet.rs:545` to decide whether to decode the
  selected skipped header (`HeaderV1::decode`, which runs the FIPS 203 modulus check on `ek_pq`, `keys.rs:197-199`, and
  allocates two boxes); the `?` returns `Rejected` before `decide` if that decode fails. Only then are `found`,
  `current_opened`, `next_opened` combined in `decide` (`:559`). So there are two conversions, the first before the
  combination — the M01-C4 shape in letter. **Refutation attempt (succeeds on impact):** the bit converted early is
  "some skipped key AEAD-opened". The AEAD already reveals it: `decrypt_inout_detached` applies the keystream only after
  a valid tag (`chacha20poly1305-0.11.0/src/cipher.rs:90-97`), so an opening costs one keystream pass over 2314 bytes
  more than a rejection (documented, `aead.rs:12-14`). The early conversion therefore adds no new information, only
  amplitude (decode ≈ µs). Functional equivalence with §7.4 ("Open() includes decoding", reading 3) holds except when
  one `hdr_ct` AEAD-opens under two different keys (negligible; when a skipped key equals `hk_r` the same plaintext
  fails decode under both, same result).
- **Repro:** read `ratchet.rs:533-559@665e84e` with `aead.rs:82-106` and the crate source above. No test can see it
  (L3-02: the ct fixture has no skipped keys).
- **Impact:** none on secrecy beyond the documented verify-then-decrypt leak; the stated security argument (D3, module
  docs) is false as written, and the code violates the letter of a docs/06 §9 guardrail.
- **Smallest fix:** either (a) correct D3 and the two module docs to name the second conversion and why it leaks
  nothing beyond `aead.rs:12-14`, or (b) make it branch-free: read `n` from the fixed offset of the selected plaintext
  (`skipped_header[38..42]`, big-endian, after `ver‖flags‖dh_pk‖pn`), compute `found` as now, and decode only on
  `Path::Skipped` after `decide`.
- **Status:** CONFIRMED (deterministic reading) · confidence high.

### L3-02 · minor · `crates/secmp-testkit/benches/ct.rs:1649-1696@665e84e` (fixture) · `:1932-1962` (targets)
- **Obligation:** CLAUDE.md §5 ("Trial decryption … must do constant work regardless of outcome"); docs/06 §4 row
  "Constant time" (`docs/06-engineering-standards.md:57@665e84e`: dudect tests for "the SecMP-TR reject paths"); plan
  D3's constant-time skipped selection (review focus L3, J9).
- **Reasoning:** the only TR fixture is B after A's cells n = 0 (step) and n = 1, delivered in order

  over zero elements, and no class has a header that opens under any key but `hk_r`. A regression that replaced the

- **Repro:** read `ct.rs:1661-1678` with `ratchet.rs:636-651`, `:599-600`; or decode `b.to_bytes()` in a kat test:
  `count` (u16 before the entries, `state.rs:223`) = 0.
- **Impact:** the J9 constant-time property is unguarded against regressions; a future non-CT scan would leak, to a
  timing observer replaying genuine cells, which old chains still have pending entries and their sizes.
- **Smallest fix:** a fourth target `tr_decrypt_reject_skipped` on a fixture with ≥ 3 chains in `skipped` (A sends
  n = 0…3, B receives n = 0, 3 → entries; step twice): class 0 = replay of a consumed late cell whose chain key is the
  first distinct skipped key, class 1 = the same for the last distinct key (both: any_skipped = 1, found = 0 →

- **Status:** CONFIRMED (deterministic reading) · confidence high.

### L3-05 · note · `crates/secmp-proto/src/tr/ratchet.rs:559-604@665e84e` (reject paths)
- **Obligation:** spec §7.4 note (b) ("one uniform error"); docs/01 metadata claims (L2's lane).
- **Reasoning:** reject *reasons* are timing-distinguishable by design: evidence medians (k = 1, M1 Pro) 9.58 µs
  (no key opens), 14.25 µs (constancy), 17.58 µs (body MAC); a replay of a delivered cell takes the constancy-depth path
  plus `skip_plan` rejection. A relay holding genuine cells can produce three of the four classes without any key
  (header garbage; replay; mauled body), and so learn from the receiver's processing time whether it still holds the
  header key of a replayed cell (chain stepped past and its skipped entries evicted or not). The *error* is uniform;
  the timing is spec-inherent.
- **Repro:** the three `calibration_median_ns` values in the evidence JSON; code paths above.
- **Impact:** acceptable only if decrypt duration and reject reason never shape network-visible behaviour (ack/fetch
  pacing, M5/M6). Also the transactional decrypt lets a relay replay one mauled far-ahead genuine cell repeatedly at up
  to 2 × 2^20 `KDF_CK` per attempt (§7.4 note (a)), each discarded — a CPU-cost, not CT, question.
- **Status:** CONFIRMED (evidence + reading); acceptability PLAUSIBLE pending L2 · confidence medium. Fan-out to L2.

### L3-07 · note · `crates/secmp-proto/src/tr/ratchet.rs:261-272`, `:519@665e84e`
- **Reasoning:** the dummy for an absent header key is the fixed all-zero key. A party that knows `sb` (AD =
  `"SecMP-TR/1 hdr" ‖ sb`) can seal a header under it; it then AEAD-opens in the absent slot (masked to not-opened) and
  costs one extra keystream pass, revealing that `hk_r` is absent (before the first received message). `sb` is the HX
  transcript, which includes `IKSPublic_I` and `EK_I` (spec §6.4, `docs/03:313-316`), so in practice only the peer can
  do this, and the protocol phase it reveals is visible to the relay anyway.
- **Impact:** negligible. A "fix" by reusing `nhk_r` as dummy would be worse (a genuine step header would then open
  twice whenever `hk_r` is absent, visible to a relay replaying it). Recommend: document as accepted.
- **Status:** PLAUSIBLE (precondition knowledge of `sb` not shown for any third party) · confidence medium.

  HMAC once and clones — constant work per step.

  (`ratchet.rs:500`, `:555`, `:594-595`, `:628`; `state.rs:333`, `:337`; `x25519.rs:64`; `msg.rs:113`).

- Trial decryption opens every candidate key every call; absent keys masked; no early exit; `decide` branches once.
- Body MAC: HMAC tag recomputed, `subtle` compare, decryption only after it (`msg.rs:106-120`). Header AEAD:
  `subtle` tag compare inside the crate (`cipher.rs:89-90`). Decaps (libcrux, implicit rejection) and X25519 (dalek)
  constant time; all-zero DH check via `ct_eq` (`x25519.rs:64`).
- No secret-indexed table lookups in the TR code or KDFs; the skipped map is a linear constant-time scan.
- ct gate: method unchanged by ADR-042 (J4); thresholds unchanged; target set enforced; A/A′ FAIL ⇒ `CONTROL_FAIL`
  enforced by bench and gate; inputs placement-independent (`blend`); TR classes reach their reject sites; measured
  codegen = release profile; evidence run verdict PASS with every TR target PASS, A/A max 2.81, A/A′ 1.44/0.75,

## Findings

### L4-01 · minor · secrets of long-lived locked keys and fresh chain keys survive on the dead stack after every TR key operation

- **Location:** `crates/secmp-crypto/src/mlkem.rs:65-73@665e84e` (`with_key_pair`: `generate_key_pair(*self.0.expose_secret())` copies the seed by value; the `MlKemKeyPair` with the 2400-byte expanded `dk` lives in the frame; `into_parts()` *moves* `sk` out and `sk[0..].zeroize()` wipes only the moved copy); `crates/secmp-crypto/src/x25519.rs:47-49@665e84e` (`StaticSecret::from(*bytes)` → dalek's `mul_clamped` copies the clamped scalar); `crates/secmp-crypto/src/kdf.rs:18-24@665e84e` via `hkdf 0.13.0` `expand_multi_info` (`prev: Option<Output<H>>` and `output` are plain stack arrays holding T(i); hkdf has no `zeroize` feature). M3 call sites: `tr/state.rs:69` (`DhPair::new` → `public_key`), `tr/state.rs:83` (`KemPair::new` → `encapsulation_key`, i.e. a full key expansion just to recompute `ek`), reached from `init_*`, every DH step (`ratchet.rs:658-659`) and **every `RatchetState::from_bytes` (`state.rs:300-301`) — every state load**; `ratchet.rs:646` (`decapsulate`), `:647/:661` (X25519), `:648/:662` (`kdf_rk`).
- **Obligation:** CLAUDE.md §1.6 ("secrets … zeroized"); docs/04 CS-2.2 (long-lived secrets only in locked, guarded pages); the code's own claim `mlkem.rs:64` "zeroise the expanded decapsulation key"; docs/06 §9 "zeroize on all paths".
- **Evidence (CONFIRMED, runtime, release and debug):** dead stack after
  - `MlKem768Dk::encapsulation_key()` / `decapsulate()` on the RPK prekey: expanded-dk chunks `dk[0..32]`, `[32..64]`, `[512..544]`, `[1120..1152]` (the encoded secret vector ŝ = the decapsulation secret) and seed half `z` (debug: also `d`);
  - `RatchetState::from_bytes` on B's state: B's `kem_s` expanded dk (same chunks) and seed `z`/`d`;
  - `X25519Secret::public_key()`: the clamped X25519 scalar of `spk` (= `dh_s` of the responder);
  - a DH step (`decrypt` on the step path): the new `ck_s` and `nhk_s` (HKDF T(2), T(3) of `KDF_RK`).
  Message keys, `rk` and plaintext were not found on the stack in these runs. The values persist until the region is overwritten (they were still present several operations later).
- **Reasoning / self-refutation:** the M1 report (`docs/reviews/M01-report.md:198`) already lists "zeroisation is best effort for values the libraries copy on the stack"; the M1 review accepted "expanded per use and zeroised" (`M01-review.md:27`). What is new: (a) the residue is the **whole expanded decapsulation secret**, not a stray byte — the `LockedSecret` protection of `dh_s`/`kem_s`/RPK is undone by an unlocked, swappable copy after each use; (b) M3 multiplies the exposure (expansion on every load, two expansions + two X25519 per step). No remote attacker reaches the dead stack; it needs process-memory disclosure, swap or a crash dump (CS-2.3 disables dumps). Hence minor, not major.
- **Repro:** `cd findings/L4-probe && CARGO_TARGET_DIR=/tmp/t L4_STACK=1 cargo run --release --offline` (copy `src/Cargo.lock` next to it first).
- **Impact:** defence-in-depth gap; makes CS-2.2's locked pages largely cosmetic for the ratchet KEM/DH keys.
- **Smallest fix:** in `secmp-crypto`, an `#[inline(never)]` stack scrub (`let mut b = [0u8; 32 * 1024]; b.zeroize(); black_box(&b)`) called by `with_key_pair`, `X25519Secret::{public_key, diffie_hellman}` and `kdf_rk`/`hkdf` callers right after the library call (safe code, no new dependency); store/derive `kem_s.ek` without a full expansion on `from_bytes` (e.g. keep `ek` in the record and check it on load, or expand lazily). Otherwise record it as an accepted residual risk next to CS-2.2 (owner/reviewer). The `findings/L4-probe` stack mode is a ready regression check.
- **Status:** CONFIRMED · confidence high (mechanism read in source; residue observed in both profiles).

### L4-02 · minor · the session root key `rk` (and the chain/header keys) live on the ordinary heap, not in locked memory

- **Location:** `crates/secmp-proto/src/tr/state.rs:102@665e84e` (`rk: SecretBytes<32>`), `:116-126` (chain/header keys), `:134` (skipped); contrast `:104`, `:108` (`dh_s`, `kem_s` in `LockedSecret`).
- **Obligation:** docs/04 CS-2.2: "Long-lived secrets (master key, IKS, **session root keys**) are stored in locked, guarded pages … `secmp-sys-mem::SecretPage`." `secmp-crypto/src/secret.rs:71-72` itself reserves `LockedSecret` for "later the master and root keys".
- **Reasoning:** `rk` lives for the whole session between DH steps (days to months for an idle contact); `SecretBytes` is a `Box` on the global heap (swappable, in dumps). Neither the report's deviations (§5) nor its risks (§7, which discusses locked memory only for `dh_s`/`kem_s`) mention it; `state.rs:4-6` presents the hygiene as complete. Counter-argument considered: docs/07 evidences CS-* in the client milestone ("master key only inside the locked page") — so the judge may treat this as a carried item rather than an M3 defect. The fact itself is not in doubt.
- **Impact:** same class as L4-01 (memory disclosure / swap), for the key that seeds every future chain until the next step.
- **Smallest fix:** a `LockedSecret`-backed root-key type for `rk` (one more locked page per session — budget it with the §7 RLIMIT risk), or an explicit ADR line scoping CS-2.2's "session root keys" and accepting heap `SecretBytes` for the ratchet.
- **Status:** CONFIRMED (deterministic reading) · confidence high on the fact, medium on the obligation reading.

### L4-03 · nit · `RatchetState::from_bytes` accepts well-formed but unreachable shapes ("restricted to reachable shapes" overclaims)

- **Location:** `tr/state.rs:278-298@665e84e`, `:325-349` (`skipped_is_canonical`); claim at `state.rs:21-27` and `docs/reviews/M03-report.md:43` ("restricted to reachable shapes").
- **Evidence (CONFIRMED, probe `L4_SHAPE=1`):** B after one step (`n_r = 1`, no skipped). Appending one entry `(hk_r, n_r + 5, mk)` → **ACCEPTED**; appending `(nhk_r, 0, mk)` → **ACCEPTED**. Neither is reachable: every stored `(hk_r, p)` has `p < n_r` (`derive_skipped` stores `p < header.n`, then `n_r = header.n + 1`), and no entry is ever stored under `nhk_r`. With the second, the next honest DH step opens under the "skipped" key first (`select::decide`), takes the Skipped path, fails the body MAC with the forged `mk`, and is rejected on every retry until evicted.
- **Totality and canonicity hold:** every read is bounded (`codec.rs:43-47`), the format byte is checked (`state.rs:239`), `count ≤ 512`, `r.finish()`, and `fuzz/fuzz_targets/tr_state.rs` asserts "accepted ⇒ re-encodes to the input" (evidence: 4 024 051 runs, no finding). Only someone who can write the encrypted store can trigger this — and that party already holds every key.
- **Smallest fix:** add the two checks (entries under `hk_r` need `n < n_r`; no entry under `nhk_r`), or reword the claim to "the listed shape checks".
- **Status:** CONFIRMED · confidence high.

### L4-04 · nit · the unreachable post-`apply` error in `decrypt_with` returns the *advanced* state as `Refused`

- **Location:** `tr/ratchet.rs:481-490@665e84e` (`self.apply(update); match self.to_bytes() { … Err(error) => Err(Refused::new(self, error)) }`); docs at `:463` and `Refused` (`:90-92`) say "the state is unchanged".

  0 executed in CI because both host jobs are skipped).

### F1-01 · minor (M3; spec-level, carry as a STOP-class item to the M6 brief) · `docs/03-protocol-spec.md:604@665e84e` (§9.3 FETCH ack rule) with `crates/secmp-proto/src/tr/ratchet.rs:559-604@665e84e`, `:636-653`, `tr/content.rs:185-192`

- **Obligation.** CLAUDE.md §1.1 / §1.4. docs/01 §3.1 says the relay cannot learn "whether a cell is real or
  cover traffic" (`docs/01-threat-model.md:46`). docs/03 §11.3 is the exhaustive list of accepted leakage
  (`docs/03:709-715`), and it contains nothing about processing time.
- **What the directorate concluded.** L3-05 / L3-08 / L3-10 call the reject-reason timing "visible by design" or
  "accepted by design". The medians are 9.6 µs (header), 14.3 µs (KEM constancy) and 17.6 µs (body MAC). L3 also
  calls the consumed-entry position and the real/dummy split after decrypt acceptable. Acceptability was left
  "pending L2", and L2 did not take it up. So the directorate has not established it.
- **What the work reveals.** Across many cells, processing time per cell separates:
  - the reject reason;
  - step from chain (≈ 0.4 ms against ≈ 20 µs: Decaps, two keygens, Encaps);
  - the gap size, at ≈ 400 ns per position (measured below);
  - the presence of skipped entries for a replayed cell's chain;
  - after decrypt, a dummy from a real message (discard against store and commit).

  To a relay that replays genuine cells, these leak chain boundaries, i.e. where the sender stepped. Those mark
  the reverse queue's deliveries, which is a cryptographic hint at which two queues form a conversation. They also
  leak real/dummy and activity statistics.
- **Where it becomes network-visible.** §9.3 lets the FETCH of slot k+1 be built "at a fixed δ before tick k+1 with
  whatever ack is committed by then" (`docs/03:604`). The cumulative `ack` therefore records whether processing of
  response k finished before the deadline.
  - The relay chooses which cells go into a response and in what order. In Balanced mode, `FETCH_MULTI` mixes
    queues (`docs/03:654`).
  - With a malicious contact as accomplice, the relay has a tunable, repeatable delay knob. The contact seals one
    header with `n = n_r + g` and a bad body MAC. Each delivery costs the victim g × `KDF_CK` and is rejected with
    the state unchanged (F1-02), so the relay can replay that one cell indefinitely.
  - The relay places it before a target cell and tunes g so that the response straddles the δ deadline. The ack
    then reflects the target's processing class.
  - Without an accomplice, the knob is ≈ 1 µs per *withheld* genuine cell. For example, 1 day withheld gives
    ≈ 10 ms, by mauling the latest withheld cell's body (rejected, repeatable).
- **Refutation attempt (partly succeeds).**
  - In Strict mode with the "build after commit" option, the leak needs processing above P_q − RTT (seconds).
  - The knob's own jitter (CPU frequency, tens of ms at 1 s) hides a sub-ms real/dummy Δ for a single cell.
  - So one-shot real/dummy classification is impractical. Aggregate statistics (activity periods, step positions)
    over many cells remain plausible.
  - Nothing in M3 code can fix this: the work difference is mandated by §7.4.
- **Impact on M3.** None on code. The directorate must not record L3-05/L3-08/L3-10 as unconditionally accepted.
  The acceptance holds only if "no network-visible behaviour depends on decrypt duration", and the spec's §9.3
  δ option breaks that condition.
- **Smallest fix.**
  - (1) In the M3 review, record L3-05/08/10 as *conditionally* accepted.
  - (2) Add a docs/09 open question or an RR entry: "ack timing must be independent of processing duration".
    Candidate remedies: a fixed one-response ack lag, or a per-slot processing budget with deferred fast-forward.
  - (3) Make it a review-focus item in the M6 brief.
- **Status.** Mechanism CONFIRMED (spec text + code reading + timing below). Exploitability PLAUSIBLE: no M6 code
  exists, and the accomplice scenario was not run. Confidence medium on the mechanism, low on practical
  per-cell power.

### F1-02 · minor · `crates/secmp-proto/src/tr/ratchet.rs:599-604@665e84e`, `:636-655`; `select.rs:105-114`; `docs/03:473` (§7.4 note (a)); `docs/01-threat-model.md:95`

- **Obligation.** docs/01 §3.3 ADV-C, which accepts only "Flood the user's queue (until eviction/quota)"
  (`:95`). docs/03 §7.4 note (a) sizes the fast-forward cost for a *returning recipient*, once per message.
- **Reasoning.** On the chain path, up to 2^20 `KDF_CK` run *before* the body MAC (`:599-604`). On a step, up to
  2^20 run for `pn` on the old chain plus 2^20 for `n` on the new chain, then the MAC (`:638-655`). That is
  2^21 + 1 `KDF_CK` = 2^22 + 2 HMACs.
  - A rejected cell discards all of it (note (c)), so the same cell costs the full amount on every delivery.
  - A contact can produce such cells at will: a header under its own `hk_s`/`nhk_s` with a large `n`/`pn` and any
    body.
  - The relay can replay one such cell without limit, and nothing ever advances.
  - L3-08 says this work is a function "of the authenticated header, not of attacker-chosen bytes". That is wrong
    for ADV-C. The header is authenticated only by a key the contact holds, and the body is not yet verified.
- **Measurement (release, x86_64 container, pinned `secmp-crypto`).** `kdf_ck` takes 347–413 ns. 2^20 take
  0.420 s; 2^21 take 0.866 s.
  - Strict mode delivers F = 4 cells per P_q = 10 s, so one malicious session costs ≈ 3.5 s of CPU per 10 s.
  - Balanced mode delivers F_M = 8 cells per 10 s, ≈ 7 s per 10 s.
  - Process: `cargo build --release --offline` of `scratchpad/f1/ffprobe` with `CARGO_TARGET_DIR=tgt`.
- **Side nit.** Report §7 says "3 × 2^20 KDF_CK for one message" (`docs/reviews/M03-report.md:294`). The code
  maximum is 2^21 + 1 (`ratchet.rs:638-653`), matching note (a)'s "≤ 2^22 HMACs".
- **Impact.** Availability and battery, plus the delay knob of F1-01. No confidentiality or integrity impact. The
  user's mitigation is deleting the contact, but a uniform `Rejected` gives the user no way to see which contact
  causes the load.
- **Smallest fix.** Spec and threat-model level, no M3 code change: an RR entry or docs/01 §3.3 row ("CPU cost up
  to ≈ 1 s per cell, repeatable"). For M6/M7, either a per-session fast-forward budget per slot, or a spec revision
  allowing a non-authoritative cache of derived chain positions across rejects. Correct report §7.
- **Status.** CONFIRMED (code reading + release measurement). Confidence high.

### F1-03 · minor (proposed upgrade of L2-04 from note) · `crates/secmp-proto/src/tr/ratchet.rs:690-717@665e84e`; `docs/01-threat-model.md:112`, `:120`; `docs/03:700`

- **Reasoning.** L2-04 framed retention as the classic Double Ratchet trade-off ("few gaps occur"). A relay can
  *force* it:
  - The relay drops one cell per chain. It cannot tell which cells are real, but dropping every k-th cell with k
    at most the chain length suffices.
  - Each dropped position is stored when a later cell or step header skips over it (`derive_skipped`, `:236-258`).
    The receiver then keeps ≤ 512 message keys whose ciphertexts the relay has recorded.
  - The window holds the 512 most recently dropped cells and is renewed as the relay keeps dropping.
  - A later ADV-T/ADV-P compromise decrypts all of them. docs/01 §3.5 states "Cannot decrypt past traffic (FS)"
    without qualification, and the TR row claims "forward secrecy per message".
- **The same lever also costs work on every cell.**
  - It keeps `skipped` at up to 512 distinct header keys, so every cell then costs 514 header opens (≈ 1 ms,
    report §7).
  - `from_bytes` grows to O(512²) `ct_eq` (`state.rs:328-349`).
  - Each cell's full-state commit is ≤ 38 585 B (`state.rs:166`). At ≈ 8 640 cells/day/direction, that is
    ≈ 0.66 GB/day of store writes per contact. These are M7 budget items.
- **Smallest fix.** An RR entry before M7 (relay-forced skipped retention), or a spec revision with an age bound
  (drop entries of chains older than N steps). Record the write volume in the M7 brief.
- **Status.** CONFIRMED (deterministic reading; the relay's capability is docs/01 §3.1 "drop"). Confidence high.

### F1-04 · note · FO-1 / L3-07: all-zero placeholder key — **REFUTED** as an attack · `ratchet.rs:261-272@665e84e`, `:519-530`, `:559`, `:576`

- **Relay.** Sealing a header that opens under the zero key needs the AD `"SecMP-TR/1 hdr" ‖ sb`. `sb` hashes
  `IKSPublic_R`, the prekeys and `IKSPublic_I` (`docs/03:313-316`). The relay sees the first two only inside
  link data encrypted under `link_key`, and the third only inside the `K_id` layer, which needs DH3/ss_spk even
  after an invitation leak (`docs/03:318-322`). The relay cannot compute `sb`, so L2's "relay-crafted header" is
  impossible.
- **State.** `open` runs on `&self` (`:509`), and the zero-key slot's `Choice` is `opened & present` = 0. The
  decrypted bytes in `current_header` are used only on `Path::Chain`, which needs `current_opened` = 1 (`:576`,
  `select.rs:62-81`). `nhk_r` is `Some` in every reachable state (`:329`, `:363`, `:703`), so only `hk_r` is ever
  replaced, and only before the first receipt. No state is influenced.
- **Timing.** At most one extra keystream pass (≈ 2330 B, about a µs), and only for a sender who knows `sb` (the
  peer), revealing a protocol phase the peer already knows.
- **Verdict.** L3-07 PLAUSIBLE → REFUTED (no exploitable effect); L2 FO-1 closed. Confidence high.

### F1-05 · note · crash windows of `Sealed::persist` / `Opened::commit` (J11, task 2c) · `ratchet.rs:127-189@665e84e`, `state.rs:193`, `:237`

- **Crash after `persist` returned Ok, before the send.** The durable state already has n_s + 1. After a restart
  the next cell uses position n_s + 1 with a fresh key, so no key is reused. One cell is lost, which spec §7.5
  accepts (`docs/03:484`). The receiver later stores a skipped key for a position that was never sent; no
  ciphertext exists for it.
- **Crash after `commit` returned Ok, before the ack.** The relay redelivers the cell. It is rejected at stale `n`
  (chain/step) or at a missing `(hk, n)` (skipped), then acked as §9.3 requires (`docs/03:604`). Nothing is lost if
  the caller wrote the message inside the commit closure. The redelivered cell cannot re-run a step with fresh
  randomness: the state already holds the step.
- **`commit` returned Err.** The `Opened` state is dropped. A send based on its new `ck_s` is impossible because
  the state is released only by `commit`, so redelivery re-steps with fresh randomness and no key is reused.
- **Residual hazards (caller side, M4/M7).**
  - (i) The doc line "On `Err` … the durable state is the previous one" (`:145-146`) holds only if the closure
    fails before durability. If the write landed and the closure then returns Err, the durable state is the *new*
    one. That is harmless (one position lost), but the sentence is inaccurate.
  - (ii) `persist(|_| Ok(()))` is accepted, and `to_bytes`/`from_bytes` are public. A caller can fork a state or
    skip durability, and then reuse an mk under §3.3's fixed IV (`docs/03:117`). This is the type-level limit of
    any closure API.
  - (iii) §6.5 requires the HX first cells to be persisted and re-sent byte-identically (`docs/03:340`). The
    closure never sees the cell, so M4 must write state and cell together after `persist`, e.g. `persist` with a
    no-op closure and then an atomic `to_bytes` + cell write. Otherwise it accepts a window in which it must
    re-seal at n_s + 1.
- **Status.** CONFIRMED (deterministic reading). There is no reuse or loss beyond §7.5 with the API as built.

## 3. Contradiction hypotheses (for verifiers)

- **H1 — Open() vs. decode.** `S:434-440` reads "if header = Open(hk, …)"; it is silent when the AEAD opens but
  HeaderV1 decoding fails. Rust (`R/tr/ratchet.rs:544-547`, `:576-577`) and ref (`P/tr.py:206-219`) both reject
  the whole cell. A literal reading where decode is part of Open would instead try the next key. The header AEAD
  is explicitly non-committing (`S:129`, `S:700`), so ADV-C can build one `hdr_ct` that opens under a skipped hk
  with bad fields and also under `hk_r`, and the two readings then give different results. The choice was made as
  "a reading adopted without a question" (`V:292`), not as an SQ or ADR. Verify that the readings really diverge
  and grade it (probably minor or note: only the peer's own messages are affected).
- **H2 — SKIP_WINDOW scope.** `S:169` says SKIP_WINDOW is "retained per receiving chain", but `S:466-468` applies
  it per `skip_message_keys` call. Code (`R/tr/select.rs:112`, `R/tr/ratchet.rs:236-258`) and ref
  (`P/tr.py:236-240`) follow `S:466-468`. Repro with the ref: deliver n=300, then n=600 on one chain → 512
  entries, all under one hk, positions 44–599. Positions more than 256 behind `n_r` are kept, against the rationale
  in `S:468` ("can no longer arrive"), and they push other chains' keys out under the 512 total. The spec is
  inconsistent; code = ref = §7.4.
- **H3 — Eviction timing.** The spec evicts at the end of each `skip_message_keys` call (`S:470`), which is twice
  on a step. Rust evicts once, in `apply` (`R/tr/ratchet.rs:714-716`); the ref follows the spec
  (`P/tr.py:241-242`). The results should be the same, since last512(last512(X‖A)‖B) = last512(X‖A‖B), and
  vector rows `V:250-256` pass. Expected verdict: REFUTED.
- **H4 — When randomness is drawn on a step.** The spec (`S:457-458`) and ref (`P/tr.py:251-253`) draw the
  sending half's keys before MsgDecrypt. Rust draws them only after the MAC (`R/tr/ratchet.rs:656-662`). Accepted
  states are the same (vectors pass). Rust never uses the DH randomness listed for N1 (`V:26`, `V:45`), and
  `TV:187-199` does not check `e.remaining()` on rejects. So the J8 claim "a rejected cell draws no randomness" has
  no evidence from the vector replay. Rust can also return `Unavailable` after an authentic step cell
  (`R/tr/ratchet.rs:658-660`), an outcome the spec does not have (J5).
- **H5 — "≤ 3 in practice".** `S:433` says the number of distinct hks is "≤ 3 in practice". A peer that steps
  every time with `pn = n_r + 1` leaves one entry per chain. That allows up to 512 distinct hks, which means 514
  header opens per cell (`R/tr/ratchet.rs:522-530`) and O(512²) `ct_eq` in `from_bytes`
  (`R/tr/state.rs:328-349`). Check this against ADV-C abuse (`T:95`) and the < 3 ms target.
- **H6 — Label outside App. A.** `"SecMP-TR/1 state-digest"` (`V:50`; `tests/common/tr_digest.rs:14`) is missing
  from App. A, which calls itself exhaustive and requires an ADR for any new label (`S:748`, `S:764`). It is used
  only in tests. SQ-24 is still open.
- **H7 — "strict +1 on receive".** `CL:74` requires a strict +1 on receive, but §7.4 allows out-of-order delivery
  and fast-forward up to 2^20 (`S:461-470`). The scope is probably LINK only. Code follows the spec.
- **H8 — Binding cross-reference.** `S:104` points to a "header-in-AD rule (§7.5)" that binds the ratchet keys and
  ciphertexts. §7.5 has no AD rule; the AD is defined at `S:421-422`. Verify that the binding argument holds on the
  skipped path, which checks neither KEM constancy nor `dh_pk` (`R/tr/ratchet.rs:561-575`).
- **H9 — Ref schema test path.** `ref/tests/test_tr.py:351-353` reads `src/SCHEMA-4.9-tr.md`
  (`ref/tools/render_schema_4_9.py:14`), but the file lives in `vectors/`. That test fails at the pin, although
  the rendered content is byte-identical. No workflow or xtask runs the ref pytest suite (grep of
  `.github/`, `xtask/` finds none). Lane L6.
- **H10 — Dummy `ts`.** The dummy has `ts` = 0 and `seq` = 0 (`R/tr/content.rs:53-58`), while §7.6 says "`ts` is
  the sender's clock" (`S:493`). The ts is E2E-only, so the relay never sees it. Check whether SQ-27 covers this
  (J13).
