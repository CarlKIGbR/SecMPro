WEISUNG M4-3 — K4a (real store) / K4b: can Kani build a MemoryPrekeyStore that holds an OPK?
Date 2026-10-01, this Mac (aarch64-apple-darwin), Kani 0.68.0 / CBMC 6.11.0, head 69d1320 + working tree.

Probe harness (temporary, removed again; never committed as a harness):

    #[kani::proof]
    fn probe_store() {
        let mut s = crate::prekeys::MemoryPrekeyStore::starting_at(1, 1);
        let r = s.issue_opk(&mut crate::tr::OsEntropy);
        assert!(r.is_ok());
    }

An OPK (`OpkSecrets`), an SPK generation (`SpkGeneration`) and therefore every invitation record (`add_record`
requires a held SPK and OPK) can only be created through `Entropy` (sealed; the only implementation without feature
`kat` is `OsEntropy`). Their secrets are `X25519Secret`/`MlKem*Dk` = `secmp_crypto::LockedSecret` =
`secmp_sys_mem::SecretPage` (mmap + mprotect + mlock; on Linux first memfd_secret through the variadic
`libc::syscall`). All of these types have private fields, so no stub written in `secmp-proto` can construct them.

Conclusion: under Kani 0.68 a MemoryPrekeyStore can hold no OPK, SPK or record without a product-code change
(e.g. a `cfg(kani)` heap backend in `secmp-sys-mem` beside its `cfg(miri)` one, or `cfg(kani)` constructors in
`prekeys`). K4b and the real-store part of K4a are therefore STOPPED (M04-report §11).
