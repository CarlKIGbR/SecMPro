E1 (WEISUNG M3-5, M3 review C7): how `blend` (crates/secmp-testkit/benches/ct.rs:1199-1204, via `blended_vec`
ct.rs:1212-1216) is compiled in the instance `tr_decrypt_reject` uses, aarch64-apple-darwin.

Bench source: bc5088b (identical in e625c79, the tree the binary was built from). Binary: `cargo bench --locked
--package secmp-testkit --features kat --bench ct --no-run --target-dir target/disasm` with
CARGO_PROFILE_RELEASE_STRIP=none and CARGO_PROFILE_BENCH_STRIP=none (the workspace release profile strips the
symbols; everything else is the gate's profile: opt-level 3, fat LTO, codegen-units 1, panic abort) →
target/disasm/release/deps/ct-46c3d08297ea7114; `llvm-objdump -d -C --no-show-raw-insn` (LLVM 22.1.8, rustup
llvm-tools of 1.98.1). `blend` and `blended_vec` have no symbol of their own: they are inlined, with `measure`,
into `ct::tr_decrypt_reject` (0x10000caa8). The stubs resolve via `llvm-objdump --macho -d --section=__TEXT,__stubs`:
0x10008259c → _calloc, 0x100082674 → _memcpy.

The per-sample prepare loop (one fresh `vec![0; len]` = calloc(len, 1) per input), then the timed window — 12 lines
quoted verbatim; the annotations after `//` are mine:

Finding: the mask `u8::from(class == 0).wrapping_neg()` does not survive as a mask. LLVM unswitches the loop on it:
a branch on the class (w20) selects, per input, `memcpy(out, base, len)` for class 1 (reads one buffer) or a NEON
XOR loop over `base` and `delta` for class 0 (reads two buffers, 4096 B each for the TR cells). Both run before the
timed window opens. A second prepare instance in the same function (0x10000ece8: `cbnz w8` on the A/A flag, `cbz x20`
on the class → `bl _memcpy`, else the XOR loop at 0x10000ed50) has the same split. The third `eor.16b` loop in the
function (0x10000e5b4) was not attributed.
